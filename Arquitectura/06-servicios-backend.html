RegistroServiciosExternos

Tabla de log inmutable — cada llamada HTTP a un servicio externo genera exactamente una fila. Permite auditoría completa, replay y análisis de tiempos.

Sin ClaveIdempotencia. La máquina de estados controla duplicados a nivel de estudio — no se requiere ClaveIdempotencia en el log de servicios. Si un paso se repite (p.ej. reenvío de OTP), se inserta una nueva fila con la nueva invocación.

DDL de la tabla

CREATE TABLE RegistroServiciosExternos (
    IdRegistro          BIGINT IDENTITY(1,1) PRIMARY KEY,
    IdEstudio           INT           NOT NULL,
    IdPaso              INT           NOT NULL,
    NombreServicio      VARCHAR(100)  NOT NULL,
    PayloadRequest      NVARCHAR(MAX) NULL,     -- JSON enviado
    PayloadResponse     NVARCHAR(MAX) NULL,     -- JSON recibido
    CodigoHTTPRespuesta INT           NULL,
    ResultadoInterpretado VARCHAR(20) NOT NULL
        CHECK (ResultadoInterpretado IN
               ('EXITOSO','FALLIDO','TIMEOUT','ERROR')),
    DuracionMs          INT           NULL,
    FechaInvocacion     DATETIME2     NOT NULL DEFAULT GETUTCDATE(),
    FechaRespuesta      DATETIME2     NULL,

    CONSTRAINT FK_RegServ_Estudio FOREIGN KEY (IdEstudio)
        REFERENCES EstudiosCredito(IdEstudio),
    CONSTRAINT FK_RegServ_Paso FOREIGN KEY (IdPaso)
        REFERENCES PasosEstudio(IdPaso)
);

Patrón BFF por Capas

El backend sigue un patrón Backend for Frontend (BFF) — cada canal (WEB, TIENDA, ADMIN) tiene su propio adaptador de entrada que normaliza la petición antes de llegar al núcleo de la fábrica.

│                   CANALES DE ENTRADA                     │
│   [ASESOR TIENDA]    [PORTAL WEB]    [ADMIN / FÁBRICA]   │
│        ↓                  ↓                  ↓           │
│   JWT_ORIGEN_TIENDA   JWT_ORIGEN_WEB    JWT_ADMIN         │
└──────────────────┬───────────────────────────────────────┘
                   │  BFF Layer (normalización y auth)
                   ▼
┌──────────────────────────────────────────────────────────┐
│              NÚCLEO DE FÁBRICAS (Core)                   │
│                                                          │
│  EstudiosCredito ──→ MáquinaEstados ──→ PasosEstudio     │
│         │                                    │           │
│         ▼                                    ▼           │
│  EvaluacionesRiesgo           RegistroServiciosExternos  │
└──────────────────┬───────────────────────────────────────┘
                   │  Adaptadores de salida
                   ▼
┌──────────────────────────────────────────────────────────┐
│               SERVICIOS EXTERNOS                         │
│  ERP_QUAC │ CORE_CREDITO │ OTP_PROVIDER │ BURO_CREDITO  │
│  LISTAS_RESTRICTIVAS │ PRESELECTA │ FOSYGA │ MOTOR_CUPO  │
│  BIOMETRIA (AWS Rekognition) │ UBICA                    │
└──────────────────────────────────────────────────────────┘

Reglas de integración

  • Toda invocación a servicio externo genera una fila en RegistroServiciosExternos — sin excepción.
  • Reintentos generan filas nuevas — no se sobreescribe la fila anterior.
  • Timeouts se registran con ResultadoInterpretado = 'TIMEOUT' y FechaRespuesta = NULL.
  • Los payloads (PayloadRequest, PayloadResponse) se almacenan como JSON en NVARCHAR(MAX) — no se parsean en la base de datos.
  • DuracionMs = diferencia en milisegundos entre FechaInvocacion y FechaRespuesta; puede ser NULL si la respuesta no llegó.

Datos sensibles en payloads. Los campos PayloadRequest y PayloadResponse pueden contener PII. El acceso a esta tabla debe restringirse al rol de auditoría (ROL_AUDITORIA_FABRICAS). No exponer estos campos en APIs de consulta estándar.

Índices de la tabla RegistroServiciosExternos

-- Consultas por estudio (más frecuente)

-- Monitoreo de servicios lentos o fallidos

Concurrencia Optimista e Idempotencia — Guía Práctica Nuevo v2.5

Dos mecanismos de protección son indispensables para un sistema financiero multicanal. Esta sección los explica con ejemplos reales del día a día en la bodega y en la web.

🔑 Idempotencia

Garantiza que ejecutar la misma operación múltiples veces produce el mismo resultado que ejecutarla una sola vez.

🔒 Concurrencia Optimista

Permite que múltiples usuarios trabajen sobre el mismo registro sin bloquearlo, detectando y rechazando modificaciones conflictivas.

Ejemplo 1 — Doble clic del asesor (Idempotencia)

Escenario real: La asesora María en la bodega de Medellín hace doble clic en el botón "Aprobar Estudio" porque la respuesta tardó 2 segundos. Su conexión es lenta.

Sin protección ❌Con ClaveIdempotencia ✅
Se crean 2 aprobaciones en la base de datosEl segundo request llega con el mismo UUID → el UNIQUE INDEX sobre ClaveIdempotencia lo rechaza instantáneamente
El cupo se desembolsa dos vecesLa API retorna HTTP 409 Conflict con next_action: ERROR_IDEMPOTENCY
Requiere proceso de reversión manual por el área de carteraEl Frontend muestra la respuesta original del primer request al asesor

Flujo técnico — Cómo funciona el UNIQUE INDEX

── Request 1 (clic 1) ─────────────────────────────────────────────────────────
POST /tienda/solicitud/EST-2026-00123/activar-cupo
Headers: X-Idempotency-Key: "idem-abc-789-xyz"
Body:    { "idValidacionAsesor": 4521, "tipoCierre": "EXPRESS" }

Backend:
  1. Verifica UNIQUE INDEX en EstudiosCredito.ClaveIdempotencia = "idem-abc-789-xyz"
  2. No existe → ejecuta la activación
  3. UPDATE EstudiosCredito SET IdEstadoActual = CUPO_ACTIVO, ClaveIdempotencia = "idem-abc-789-xyz"
  4. Retorna HTTP 200 { "next_action": "FINAL_SUCCESS", ... }

── Request 2 (clic 2, 800ms después) ─────────────────────────────────────────
POST /tienda/solicitud/EST-2026-00123/activar-cupo
Headers: X-Idempotency-Key: "idem-abc-789-xyz"   ← mismo UUID

Backend:
  1. Verifica UNIQUE INDEX en EstudiosCredito.ClaveIdempotencia = "idem-abc-789-xyz"
  2. YA EXISTE → no ejecuta nada, retorna la respuesta cacheada del request 1
  3. Retorna HTTP 409 { "next_action": "ERROR_IDEMPOTENCY", "original_response": {...} }

Frontend:
  Recibe HTTP 409 → muestra la pantalla de "Cupo activado exitosamente" (respuesta original)

Ejemplo 2 — Cliente y asesor abren el estudio al mismo tiempo (Concurrencia Optimista)

Escenario real: El cliente Juan abre su estudio en su celular (flujo web) para actualizar su dirección. Al mismo tiempo, el asesor Pedro lo tiene abierto en el PC de la bodega para agregar una nota sobre la visita.

T+0:00  Juan (celular)  abre el estudio → Backend retorna { VersionFila: "0x00000000000007D1" }
T+0:00  Pedro (PC)      abre el estudio → Backend retorna { VersionFila: "0x00000000000007D1" }
         (ambos tienen la misma versión de la fila — el estudio no ha sido modificado)

T+0:15  Juan actualiza su dirección:
          PUT /web/solicitud/EST-2026-00123/datos-direccion
          Body: { "ciudad": "Manizales", "VersionFila": "0x00000000000007D1" }

Backend:
  UPDATE EstudiosCredito
  SET CiudadCapturada = 'Manizales', VersionFila = NEXT_ROW_VERSION()
  WHERE IdEstudio = 123
    AND VersionFila = 0x00000000000007D1  ← condición de concurrencia

  → Afecta 1 fila ✓  → Nueva VersionFila: "0x00000000000007D2"
  → HTTP 200 { "next_action": "ADVANCE_STEP" }

T+0:18  Pedro agrega nota (tiene aún VersionFila vieja = 0x7D1):
          POST /tienda/solicitud/EST-2026-00123/agregar-nota
          Body: { "nota": "Cliente vive cerca del parque", "VersionFila": "0x00000000000007D1" }

Backend:
  UPDATE EstudiosCredito
  SET NotaAsesor = 'Cliente vive cerca del parque', VersionFila = NEXT_ROW_VERSION()
  WHERE IdEstudio = 123
    AND VersionFila = 0x00000000000007D1  ← ya no coincide (está en 0x7D2)

  → Afecta 0 filas ✗
  → HTTP 409 { "next_action": "ERROR_CONCURRENCY",
               "mensaje": "Este estudio fue modificado por otro usuario. Recarga para ver los cambios." }

Pedro recibe la alerta → recarga → ve la dirección actualizada por Juan → puede agregar su nota con la nueva versión.

¿Por qué concurrencia optimista es mejor que bloqueo pesimista?

AspectoConcurrencia Optimista ✅Bloqueo Pesimista
Congela la filaNo — múltiples usuarios pueden leer librementeSí — bloquea la fila para todos los demás desde que se abre el registro
EscalabilidadAlta — no hay recursos retenidos en el servidor de BDBaja — si el asesor abre un estudio y va a almorzar, la fila queda bloqueada por horas
Riesgo de deadlockNinguno — los conflictos se detectan al momento de escrituraAlto — dos procesos esperando locks del otro generan deadlocks
Implementación en SQL ServerVersionFila ROWVERSION — columna automática, cero código adicionalWITH (UPDLOCK, HOLDLOCK) — gestión manual de transactions
Frecuencia de conflictos realMuy baja — los conflictos simultáneos genuinos son raros en el flujo normalIrrelevante — bloquea siempre, aunque no haya conflicto

Decisión de diseño: El campo VersionFila ROWVERSION ya está en EstudiosCredito. SQL Server lo actualiza automáticamente en cada UPDATE. El LOS solo necesita incluirlo en el WHERE de cada actualización y retornarlo en cada respuesta dentro del campo meta.row_version.

Ejemplo 3 — Timeout de red en creación web (Idempotencia en móvil)

Escenario real: El cliente Andrés envía su solicitud desde su celular con señal 3G débil en el centro de Bogotá. El request llega al servidor y se procesa exitosamente, pero la respuesta nunca regresa al celular (timeout de red).

T+0:00  Andrés presiona "Enviar solicitud"
T+0:01  App genera UUID: "idem-ANR-2026-6677" y lo almacena en sessionStorage
T+0:01  POST /web/solicitud/iniciar
        Headers: X-Idempotency-Key: "idem-ANR-2026-6677"
        Body:    { "nit": "1023456789", "canal": "WEB" }

T+0:04  Backend procesa exitosamente:
          INSERT EstudiosCredito → IdEstudio: EST-2026-04521
          HTTP 200 { "study_id": "EST-2026-04521", "next_action": "RENDER_SCREEN", ... }

T+0:04  ⚡ Timeout de red — la respuesta se pierde en tránsito. El celular no recibe nada.

T+0:06  App detecta timeout (>5 segundos sin respuesta)
T+0:06  App reintenta automáticamente con el MISMO UUID:
        POST /web/solicitud/iniciar
        Headers: X-Idempotency-Key: "idem-ANR-2026-6677"  ← idéntico al anterior

T+0:07  Backend detecta que "idem-ANR-2026-6677" ya fue procesado:
          NO crea un segundo EstudiosCredito
          Retorna la respuesta original cacheada:
          HTTP 200 { "study_id": "EST-2026-04521", "next_action": "RENDER_SCREEN", ... }

T+0:07  App recibe la respuesta → Andrés ve la pantalla de "Datos básicos" sin saber que hubo un retry ✓

Reglas de implementación de Idempotencia en el LOS

ReglaDetalle
Header obligatorio en mutacionesTodo POST/PUT/PATCH debe incluir X-Idempotency-Key: {uuid}. El servidor retorna HTTP 400 si falta en operaciones que lo requieren.
TTL del registroLas claves de idempotencia se mantienen por 24 horas. Después de ese periodo, el mismo UUID puede reutilizarse (muy improbable en la práctica).
GET/HEAD son idempotentes por definiciónLas consultas no necesitan X-Idempotency-Key — releer siempre retorna el estado actual sin efectos secundarios.
Respuesta en 409El HTTP 409 por idempotencia incluye la respuesta original en original_response. El Frontend puede usarla directamente.
Generación del UUIDEl UUID debe generarse en el cliente (Frontend/App) antes de enviar el request, no en el Backend. Esto garantiza que el mismo intento tenga siempre el mismo UUID aunque haya retries.
