Plan de Trabajo — API Flujo Tienda

Fabricas de Credito QUAC — Construccion de APIs REST — 6 Capas / 9 Bloques funcionales

Version: 1.5
Fecha: 2026-05-04
Proyecto: Fabricas de Credito QUAC
Arquitectura: 6 capas (Core + BFF Tienda + BFF Web + BFF Handoff + BFF Admin + Util/Ext)

Resumen Ejecutivo

Este plan de trabajo establece la hoja de ruta para construir las APIs REST que permiten ejecutar el Flujo de Tienda completo, desde el ingreso del cliente hasta la activacion del cupo. El flujo se divide en 4 bloques funcionales que agrupan 15 endpoints y 20 servicios externos.

Validacion DB completa: FABRICASv2.sql fue validado contra Definición funcional.html (153 pasos). Todos los gaps identificados fueron resueltos (celulares separados, duplicidades, MoraComerciosAliados, RenunciaCupo, EscalamientosFabrica).

Resultado buscado: API completamente funcionales que permitan ejecutar el flujo de tienda desde la interfaz de la tienda fisica, incluyendo validaciones deidentity, calculo de cuotas, verificacion biometrica y activacion del credito.

Arquitectura de 6 capas (ref: documentacion-arquitectura-v2.html):

  • Core (22): Lógica de negocio pura. Sin conocimiento de canal. Solo mTLS interno.
  • BFF Tienda (19): Orquestación por canal. Delega a Core. Expuestos al frontend.
  • BFF Web (17): Autogestión para portal de clientes.
  • BFF Handoff (4): Biometría en celular del cliente via link SMS.
  • BFF Admin (83): CRUD de maestros y parametrización — 4 schemas, 83 SPs (Roles: ADMIN_FABRICAS).
  • Utilitarios (12) + Externos (12): OTP, SMS, Email, Storage + Buró, OCR, FOSYGA, UBICA.

Objetivo

Construir un conjunto de APIs REST que permiten ejecutar el flujo completo de solicitud de credito en una tienda fisica (Tienda QUAC), desde la captura del documento hasta la activacion del cupo preaprobado, siguiendo los diagramas Mermaid documentados en flujos/index.html.

Objetivos especificos

  • Bloque 1 (Ingreso): Validar documento, verificar existencia en ERP, consultar estado de cupo activo/bloqueado/eliminado (incluye RenunciaCupo)
  • Bloque 2 (Captura): Capturar datos del cliente, celularPrincipal + celularWhatsApp separados, email, direccion, tokenizar consentimientos
  • Bloque 3 (Validaciones): Consultar listas restrictivas, bureo de credito + mora en comercios aliados (MoraComerciosAliados), evaluacion Preselecta, validacion FOSYGA/ADRES (cotizaciones), calculo de cupo
  • Bloque 4 (Resultado): Verificacion biometrica, generacion token activacion, confirmacion token, activacion en UBICA,可能的 escalamiento a Fabrica de Soporte

Alcance

Incluido:

  • Diseno de contratos de API (OpenAPI/Swagger)
  • Implementacion de endpoints REST
  • Integracion con servicios externos (ERP, Core Credito, Preselecta, FOSYGA/Cotizaciones, UBICA, Biometria)
  • Maquina de estados para control de flujo
  • Registro de invocaciones (logging)
  • Manejo de errores y reintentos
  • Escalamiento a Fabrica de Soporte

Actualizacion v1.2 con Taxonomia de Servicios (ref: documentacion-arquitectura-v2.html):

  • Arquitectura de 6 capas: Core (22) + BFF Tienda (19) + BFF Web (17) + BFF Handoff (4) + BFF Admin (83) + Utilitários (12) + Externos (12)
  • Cada endpoint BFF delega a servicios Core internos
  • Modelo "Estado Dirigido por el Sistema" + payload estandar con next_action
  • Session Handoff para biomatria viaSolicitudesRecarga

Excluido (fuera del alcance de esta fase):

  • Interfaz de usuario de la tienda (frontend)
  • Integracion con sistema de inventario/tienda (POS)
  • Flujo Web (autoservicio) - se documenta pero no se implementa
  • Flujo Externo (asesor de campo) - se documenta pero no se implementa

Patrón de delegación: Los BFFs (T-01 a T-19, W-01 a W-17) delegan en Core services (C-01 a C-27). Los Core services pueden invocar utilitários (U-01 a U-12) y adaptadores externos (E-01 a E-16). Esta separación asegura que la lógica de negocio sea inmutable y reusable entre canales.

Procedimientos Almacenados — 1 SP mínimo por servicio

Cada servicio de la taxonomía tiene al menos un procedimiento almacenado asociado que encapsula su lógica de negocio. Los SPs son la única vía de escritura directa a las tablas de la base de datos — ninguna API escribe directamente sin pasar por un SP.

Detalle de Tareas

Nomenclatura: Los endpoints a implementar son los definidos en la Taxonomía de Servicios. No existe ningún path /api/estudio/... — esos eran prototipos de versiones anteriores. Los paths reales son /core/..., /tienda/..., /util/..., etc.
