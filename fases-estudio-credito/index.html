Fases del Estudio de Crédito QUAC

Proyecto: Fábricas de Crédito Fecha: 2026-03-19 Autor: Análisis arquitectónico Enfoque: Working Backwards

1. Contexto y objetivo

Este es el documento de análisis arquitectónico del flujo de estudio de crédito QUAC. Está dirigido a los desarrolladores que van a implementar el backend y frontend del nuevo flujo, y al coordinador del proyecto para validar que las decisiones están alineadas con la visión de negocio.

¿Por qué se necesita?

El prototipo HTML del flujo de tienda física ya existe con 13 pasos y 11 escenarios, pero falta un documento que responda: ¿quién hace qué en cada fase, con qué servicios, y cuáles hay que construir? Sin este mapa, no se puede planificar la implementación del backend.

Los 3 canales convergen

QUAC tiene 3 canales de solicitud de cupo. Los 3 pasan por las mismas 13 fases de validación. Lo que cambia es quién ejecuta cada acción manual.

Canal 1
Web Online

El cliente ingresa a preaprobado.quac.co y se autogestiona. Ingresa sus datos, toma fotos y completa el proceso sin asistencia.

Autoservicio
Canal 2
Externos (Asesor de campo)

Un asesor externo busca personas interesadas, se autentica con reconocimiento facial y va ingresando los datos del cliente.

Asesor guía el proceso
Canal 3
Tienda física

El cliente llega a comprar y solicita el cupo. El cajero actúa como asesor e ingresa la solicitud desde QuacOne (ERP).

En punto de venta

El flujo base se diseñó para el canal de tienda física. Ciertas fases contienen puntos de delegación: acciones que el asesor puede delegar al cliente enviándole un link por SMS.

3. Matriz de responsabilidades por fase

Cada fase documenta los 3 actores (asesor, sistema, cliente), los servicios involucrados y las reglas de negocio. Haz clic en cada fase para expandir los detalles.

1
Consulta de documento
El asesor ingresa tipo y número de documento
MANUAL
Condición de entradaInicio del proceso. El cliente se presenta en la tienda.
AsesorSolicita al cliente su tipo y número de documento de identidad. Ingresa los datos en el sistema.
SistemaMuestra formulario con campos: tipo de documento (CC, CE) y número de documento. Registra tienda y asesor/cajero logueado automáticamente.
ClienteProporciona su documento de identidad al asesor.
ServiciosNinguno — solo captura de datos en frontend.
Reglas de negocioEl número de documento debe ser numérico (4-10 dígitos). El tipo predetermina CC (Cédula de Ciudadanía).

SistemaConsulta si el cliente existe en el sistema. Evalúa: (a) ¿Tiene cartera activa, morosa o cancelada? (b) ¿Ya existe un proceso de solicitud en curso? Determina si puede continuar, rechazarse o reactivarse rápidamente.
ClienteEspera el resultado.

POST Credito/ConsultarProcesoSolicitud (QuacOne API) EXISTE

7
Validación FOSYGA
Solo si cliente tiene >= 55 años
AUTOMÁTICA / CONDICIONAL
Condición de entradaFase 6 completada (viable por Preselecta). Solo si el cliente tiene 55 años o más. Si es menor de 55, se salta directo a Fase 8.
AsesorObserva el loader. No interviene.
SistemaConsulta FOSYGA/ADRES para verificar: (a) ¿Registra información? (b) ¿Ha cotizado en los últimos 4 meses consecutivos? Si no cotiza → cierre no exitoso. Si no registra info → evaluar derivación a fábrica.
ClienteEspera el resultado.
ServiciosPOST FOSIGA/Consultar (QuacOne API) PARCIAL — existe en SigmaApiErpQuac pero falta confirmar integración completa con ADRES
Reglas de negocioEdad mínima: configurable vía var_env, sugerido 55 años. Registra info + cotiza → CONTINÚA. No cotiza → FIN. No registra info → derivar a fábrica. Timeout: 30s → derivar a fábrica.
Resultados posiblesCONTINÚA → Fase 8 / FIN (no cotiza) / FÁBRICA (no registra, timeout)
8
Cupo preaprobado
Cálculo de cupo según score y estrategia
AUTOMÁTICA
Condición de entradaFase 6 completada (si < 55 años) o Fase 7 completada (si >= 55 años, cotiza en FOSYGA).
AsesorObserva resultado. Informa al cliente el cupo preaprobado.
SistemaCalcula cupo preaprobado basándose en: score Preselecta, nivel de riesgo, variables de la estrategia de crédito vigente. Registra el cupo en la solicitud.
ClienteRecibe la noticia del cupo preaprobado. Decide si desea continuar.
ServiciosPOST Credito/AsignarCupo (QuacOne API) EXISTE
Reglas de negocioCupo según reglas del módulo de Estrategias (AdminSistemaQuacMFE). El cupo es preaprobado — puede cambiar en fases posteriores (UBICA, Fábrica).
Resultados posiblesCONTINÚA → Fase 9

MANUAL

SistemaPresenta formulario con listas desplegables para departamento y ciudad (parametrización DANE). Valida campos requeridos. Almacena la dirección.

Resultados posiblesCONTINÚA → Fase 10
10
Prueba de vida y validación de fotos
Selfie + fotos documento + comparación facial
DELEGABLE
Condición de entradaFase 9 completada (dirección registrada).
AsesorElige método de captura: (a) Link al cliente: SMS con link → cliente toma selfie + fotos desde su celular. (b) Cámara del PdV: Fotos presenciales. Si fotos ya se tomaron en Fase 3 por OCR, el sistema las reutiliza.
SistemaSub-fase 10a — Fotos documento: Si no se tomaron en F3, solicitar frontal + posterior. Validar etiquetas, no es copia, texto legible.
Sub-fase 10b — Verificación datos: Cruzar OCR vs datos ingresados.
Sub-fase 10c — Datos adicionales: Lugar de nacimiento, estatura, grupo sanguíneo (informativos).
Sub-fase 10d — Prueba de vida: Selfie frontal → Face Liveness → buscar en base suplantadores → CompareFaces vs documento.
Resultado: Si match < 85% → 2 intentos, luego derivar a fábrica.
ClienteSi se delega: recibe link, abre cámara, toma fotos y selfie. Si no: se posiciona frente a la cámara del PdV.
ServiciosPOST photos/validate-front-document (api-activacion-v2) EXISTE
POST photos/validate-reverse-document (api-activacion-v2) EXISTE
POST photos/validate-selfie (api-activacion-v2) EXISTE
POST Rekognition/CompareFaces (AWS Rekognition) EXISTE
Reglas de negocioOrden estricto: Fotos doc → Verificación datos → Prueba de vida. Umbral coincidencia facial: configurable (default 85%). Máx 2 intentos fotos, 2 intentos selfie. Face Liveness obligatorio. Detección de suplantación obligatoria.
Resultados posiblesCONTINÚA → Fase 12 (salta F11) / FÁBRICA → Fase 11 (fotos inválidas, match bajo, suplantación)
11
Gestión Fábrica de Créditos
Solo si una fase previa deriva aquí
CONDICIONAL
Condición de entradaDerivación desde Fase 7 (FOSYGA sin info), Fase 10 (fotos inválidas, match facial bajo), o Fase 12 (UBICA inconsistente).
AsesorVe que el estudio fue derivado a Fábrica. Informa al cliente que será revisado por un operador y recibirá notificación. Puede volver a la mesa de estudios.
SistemaCrea caso de revisión manual en la bandeja de Fábrica. Registra motivo de derivación, fase de origen y toda la información recopilada.
ClienteRecibe notificación (SMS/WhatsApp) de que su solicitud está en revisión. Puede consultar estado en el portal. Si operador solicita repetir foto, recibe link para subir nueva.

Resultados posiblesCONTINÚA → Fase 12 (operador aprueba) / FIN (operador rechaza)
12
Definición UBICA
Verificación de datos de contacto con TransUnion
AUTOMÁTICA
Condición de entradaFase 10 completada (prueba de vida exitosa) o Fase 11 completada (fábrica aprobó).
AsesorObserva resultado. Si exitoso, continúa. Si requiere gestión manual, informa al cliente.
SistemaConsulta UBICA/TransUnion para obtener datos de contacto registrados (celular, correo, dirección). Compara datos UBICA vs solicitud. Si coinciden: CONTINÚA. Si no: Evalúa antigüedad celular: ≥ 4 meses → llamada IA verificación. < 4 meses → derivar a fábrica. Si sospecha suplantación → derivar.
ClienteSi UBICA requiere verificación por llamada: contesta la llamada.

4. Módulo Fábrica de Créditos

¿Qué es? La Fábrica de Créditos es el módulo donde operadores de crédito humanos validan manualmente las solicitudes que el sistema no pudo aprobar automáticamente. Es la red de seguridad del flujo: cuando una validación falla o genera dudas, el caso se deriva aquí en lugar de rechazarse.

Nota: Este documento describe la visión general. El diseño detallado se desarrollará en ANALISIS-MODULO-FABRICAS.md.

Motivos de derivación

MotivoFaseDescripción
Fotos documento inválidas (2 intentos)F10Nitidez insuficiente, bordes no detectados, código de barras ilegible
Match facial bajo (2 intentos)F10Comparación facial selfie vs documento retorna < 85%
Suplantación detectadaF10Rostro del selfie coincide con registro en base de suplantadores
Fotomontaje o documento falsificadoF10Etiquetas Rekognition detectan indicadores de copia o falsificación
FOSYGA sin informaciónF7Cliente ≥ 55 años no registra información en FOSYGA
FOSYGA timeoutF7El servicio no respondió en 30 segundos
UBICA inconsistenteF12Celular diferente al de UBICA con antigüedad < 4 meses
UBICA — posible suplantaciónF12Llamada de verificación contestada pero con posible suplantación

Acciones del operador

  • Ver información completa de la solicitud: datos recopilados, historial de intentos, resultados de validaciones
  • Ver fotos cargadas con checklist: frontal, posterior, selfie, con indicadores de qué falló
  • Marcar foto individual: ✓ Aprobada / ✗ Repetir / ✗ Rechazada
  • Detectar fotomontajes o documentos falsificados
  • Dar visto bueno parcial o total
  • Solicitar información adicional al cliente

Flujo de ida y vuelta

Operador marca "repetir foto posterior"
    ↓
Sistema notifica al cliente (SMS/WhatsApp con link)
    ↓
Cliente abre el portal, ve qué foto debe repetir
    ↓
Cliente toma y sube nueva foto desde el portal
    ↓
Solicitud vuelve a la bandeja del operador
    ↓
Operador revisa nueva foto → aprueba o rechaza

Decisión: El módulo FabricasQuacMFE actual (Next.js 15, port 40002) no sirve como base para el nuevo flujo. Se hará rediseño desde cero.

7. Alternativa: Truora como proveedor de validación de identidad

¿Qué es Truora? Empresa especializada en validación de identidad digital para LATAM. Ofrece una plataforma integral que cubre OCR de documentos, validación facial, prueba de vida, detección de fraude y validación de contacto — todo lo que hoy armamos manualmente con AWS Rekognition + lógica propia.

La propuesta es evaluar Truora como reemplazo o complemento de la implementación actual de las Fases 3, 10 y parcialmente 12.

Comparación: Rekognition actual vs. Truora

Opciones de integración

Opción A: Truora reemplaza Fases 3 y 10 completas

Impacto: Se elimina activacion-quac-client (frontend Vue) y se simplifica drásticamente api-activacion-v2. El 80% de la lógica de validación de fotos la absorbe Truora.

Fase 3 (OCR):
  ANTES:  Cámara PdV → api-activacion-v2 → Rekognition + Gemini → lógica propia
  AHORA:  iframe Truora → OCR + validación autenticidad → webhook

Fase 10 (Prueba de vida):
  ANTES:  Link SMS → activacion-quac-client (Vue) → Rekognition (5 llamadas)
  AHORA:  Link SMS → iframe Truora → selfie + liveness + anti-fraude → webhook
Opción B: Truora como complemento (híbrido)

Usar Truora solo para prueba de vida y detección de fraude (Fase 10), manteniendo OCR con Gemini Vision (Fase 3).

Impacto: Menor — solo se reemplaza la biometría. Se mantiene el OCR existente.

Opción C: Truora solo para delegación al cliente

Usar Truora cuando el asesor delega (link SMS). Para captura presencial en PdV, mantener Rekognition.

Impacto: Se cubre delegación sin reescribir el flujo presencial.

Ventajas clave para QUAC

  1. Liveness pasiva: El cliente solo mira a la cámara — mejor UX para personas mayores (segmento FOSYGA ≥ 55 años).
  2. Detección de deepfakes: Rekognition no tiene esta capacidad.
  3. TruFace (base de fraude LATAM): Más completa que nuestra colección propia.
  4. Eliminación de activacion-quac-client: El frontend Vue y toda su lógica desaparecen.
  5. Delegación nativa: iframe Truora funciona en mobile sin desarrollo adicional.
  6. Flujo por WhatsApp: Validación completa por WhatsApp — alternativa al link SMS.

9. Plan de trabajo propuesto

El plan se organiza por producto, no por disciplina. Un mismo equipo trabaja APIs, modelo de datos y pantallas de su producto. Se incluyen puntos de socialización obligatorios antes de implementar módulos complejos, y algunos módulos se diseñan en detalle cuando llega su turno.

Los 3 productos

Q QuacOne (Tienda)
  • Front: MFE del flujo de estudio para el asesor (13 fases) + MFE Fábrica (rediseño)
  • Back: API .NET — servicios del flujo de crédito, integraciones externas (Preselecta, FOSYGA, UBICA, Rekognition)
  • BD: SQL Server — fuente de verdad del proceso de crédito. Tablas y SPs
  • Es el sistema central: aquí se construyen los servicios que todos consumen
P Preaprobado.quac.co (Web)
  • Front: Flujo de autogestión del cliente + portal de estado de solicitud
  • Back: API Laravel — orquesta qué se muestra al cliente, consume servicios de QuacOne
  • BD: MySQL — tablas operativas (logs, sesiones, estado de navegación). No es fuente de verdad del crédito
  • Incluye servicios utilitarios propios: integración Rekognition/Truora, logs de actividad
D Modelo de datos (SQL Server)
  • Fuente de verdad de todo el proceso de crédito
  • Auditar tablas existentes del proceso de fábricas
  • Diseñar tablas nuevas según se necesiten por sprint
  • SPs que soportan los servicios de QuacOne
  • Transversal a ambos productos — pero pertenece al equipo QuacOne

Principio: QuacOne construye los servicios del flujo de crédito → Preaprobado.quac.co los consume para el canal web → SQL Server es la fuente de verdad que soporta ambos. Las tareas de APIs, BD y pantallas las hace el equipo del producto correspondiente.
