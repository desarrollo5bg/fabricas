Arquitectura de Datos v2.6 — Fábricas de Crédito QUAC

Motor: SQL Server 2019+ Versión: 2.7 Fecha: 30 de abril de 2026 Tablas Nuevas: 31 Tablas Modificadas: 1

Este documento describe el modelo de datos empresarial versión 2.3 para el Sistema de Otorgamiento de Crédito (Loan Origination System - LOS) de QUAC. Esta versión implementa la "Fusión Inteligente": reutiliza las tablas existentes en producción del ERP QUAC y les añade capacidades de trazabilidad, auditoría y automatización sin romper la operación actual. La versión 2.2 añadió el sistema de detección de fraude y escalamiento con 6 nuevas tablas especializadas. La versión 2.3 añade el módulo de gestión de fotografías con 5 nuevas tablas para el ciclo de vida completo de fotos obligatorias, revisión humana y re-subida via link. La versión 2.4 documenta la Taxonomía de Servicios Backend con el diseño completo de APIs omnicanal (Web, Tienda, Handoff) y la estrategia Estado Dirigido por el Sistema. La versión 2.5 añade la División de Responsabilidades Backend vs Frontend y la Autenticación Biométrica de Asesores. La versión 2.4 eliminó las columnas de idempotencia (ClaveIdempotencia y VersionFila) ya que la máquina de estados garantiza consistencia. La versión 2.6 refleja la Auditoría DDL — 18 gaps cerrados: tabla FotografiasEstudio unificada para proceso biométrico, nueva tabla AuditoriaLogins y columnas adicionales en EstudiosCredito (NitComercio, CelularCliente).

Innovación clave: A diferencia de un diseño desde cero, esta versión respeta el trabajo existente integrando las tablas QUAC.dbo.bodegas, QUAC.dbo.KCRM_CadenaCreditos y operadores, mientras añade la capa de configuración (máquina de estados), transaccional y auditoría que faltaba. Para QUAC.dbo.terceros se creó una tabla propia (TercerosFabricas) que lee de ella mediante FK por NIT, sin alterar la tabla de producción.

5 Tablas de Configuración

6 Tablas Transaccionales

1 Tabla Propia (terceros)

TercerosFabricas como fuente de verdad. Lee de terceros sin modificarlo.

Principales mejoras sobre el diseño anterior

  • Máquina de estados inmutable — Cada cambio de estado genera un registro en HistorialEstados que permite reconstruir la línea de tiempo completa.
  • Auditoría de datos mutables — Cualquier cambio en datos del cliente durante un estudio se registra en AuditoriaCambiosDatos.
  • Logging completo de servicios — Cada invocación a buró, biometría, FOSYGA, UBICA, OTP queda registrada con el payload completo en RegistroServiciosExternos.
  • Cursor de pausa/reanudación — El campo IdPasoActual en EstudiosCredito permite que el cliente abandone y retome el proceso.
  • Parameterización total — Las reglas de negocio (días de enfriamiento, intentos OTP, timeouts) están en ConfiguracionReglasNegocio y pueden cambiarse sin deploy.

Arquitectura del Modelo de Datos

El modelo se organiza en 4 grupos lógicos que respetan el orden de dependencia (maestras → configuración → transaccionales → auditoría):

1

Tablas Existentes del ERP (Extendidas + Tabla Propia)

QUAC.dbo.bodegas, QUAC.dbo.KCRM_CadenaCreditos (extendidas). TercerosFabricas es tabla propia que lee de terceros mediante FK por NIT sin modificar la tabla de producción. GAP-19: fab.OperadoresFabrica y fab.DisponibilidadOperadores reemplazan la necesidad de modificar BERP_FABRICASOperadores.

2

Tablas de Configuración (Nuevas)

Definen el flujo, estados y reglas de negocio. FasesEstudio, PasosEstudio, CatalogoEstados, TransicionesEstado, ConfiguracionReglasNegocio. Permiten modificar el comportamiento sin tocar código.

3

Tablas Transaccionales (Nuevas)

Registran las operaciones del proceso. EstudiosCredito (orquestador central), RetosSeguridad, EvaluacionesRiesgo, RegistrosBiometria, ValidacionesContactabilidad, ConsentimientosLegales.

4

Tablas de Auditoría (Nuevas)

Trazabilidad inmutable. HistorialEstados, AuditoriaCambiosDatos, RegistroServiciosExternos. REGLA: Solo INSERT, nunca UPDATE ni DELETE.

Estrategia de Integración

Principio rector: Las tablas existentes NUNCA se eliminan ni se altera su estructura original. Solo se les añaden columnas al final mediante ALTER TABLE ADD. Esto garantiza backwards compatibility con el ERP QUAC existente. Excepción: QUAC.dbo.terceros es demasiado grande para modificar, por lo que se crea una tabla propia que lee de ella mediante FK por NIT.

Estrategia para QUAC.dbo.terceros

-- Tabla PROPIA que referencia a terceros sin modificarlo:
CREATE TABLE dbo.TercerosFabricas (
    IdTerceroFabricas       INT IDENTITY(1,1) NOT NULL,
    NitTercero              VARCHAR(20) NOT NULL,  -- FK a terceros.nit
    NombreTercero           VARCHAR(200) NULL,
    EstadoTercero           VARCHAR(20) NOT NULL DEFAULT 'ACTIVO',
    TieneCupoActivo        BIT NOT NULL DEFAULT 0,
    EstaBloqueadoFabricas  BIT NOT NULL DEFAULT 0,
    MotivoBloqueo          VARCHAR(100) NULL,
    FechaBloqueo           DATETIME2 NULL,
    FechaDesbloqueo        DATETIME2 NULL,  -- Cooling-off
    TieneRegistroBiometrico BIT NOT NULL DEFAULT 0,
    PuntajeCredito         DECIMAL(5,2) NULL,
    FechaCreacion          DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    FechaModificacion      DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    ...
    CONSTRAINT FK_TercerosFabricas_Terceros FOREIGN KEY (NitTercero)

    → EstadoRevision: APROBADA_AUTO | RECHAZADA

[2] DOCUMENTO_FRONTAL
    → Captura cara frontal del documento de identidad
    → Comparación facial con SELFIE (PorcentajeCoincidencia)
    → Revisión AUTO o MANUAL_ASESOR

[3] DOCUMENTO_TRASERO
    → Captura cara trasera del documento
    → Validación OCR (lectura de datos)

Flujo del Proceso (13 Pasos)

El flujo completo de otorgamiento se divide en 7 fases con 13 pasos configurables.

1

FASE 1: Identificación (3 pasos)

INGRESO_DOCUMENTO — El asesor digita el documento del cliente.

VALIDAR_EXISTENCIA — Verifica si existe en ERP QUAC. Actor: SISTEMA. Servicio: ERP_QUAC. Timeout: 30s.

VALIDAR_CUPO_BLOQUEO — Verifica cupo activo, bloqueos, mora. Actor: SISTEMA. Servicio: CORE_CREDITO. Timeout: 30s.

2

FASE 2: Datos del Cliente (1 paso)

CAPTURA_DATOS — Captura o actualización de datos personales, correo, celular, dirección. Actor: ASESOR.

3

FASE 3: Consentimiento Legal (2 pasos)

CONSENTIMIENTO_DATOS — El cliente acepta términos y autoriza tratamiento de datos. Actor: CLIENTE.

TOKENIZACION — Envío de OTP por WhatsApp/Email y validación. Actor: SISTEMA. Servicio: OTP_PROVIDER. Timeout: 120s.

4

FASE 4: Validaciones de Riesgo (4 pasos)

VALIDAR_LISTAS — Consulta listas restrictivas. Servicio: LISTAS_RESTRICTIVAS. Timeout: 30s.

CONSULTAR_BURO — Consulta historial crediticio. Servicio: BURO_CREDITO. Timeout: 60s.

EVALUAR_PRESELECTA — Motor de decisión. Servicio: PRESELECTA. Timeout: 60s.

VALIDAR_FOSYGA — Verificación seguridad social. Servicio: FOSYGA. Timeout: 30s.

5

FASE 5: Límite de Crédito (1 paso)

CALCULAR_CUPO — Cálculo del límite preaprobado según score. Servicio: MOTOR_CUPO. Timeout: 30s.

6

FASE 6: Verificación de Identidad (1 paso)

VERIFICACION_BIOMETRICA — Captura facial, prueba de vida, OCR. Servicio: BIOMETRIA. Timeout: 120s. Requiere intervención: Sí.

7

FASE 7: Activación (1 paso)

ACTIVACION_CUPO — Validación UBICA y activación automática o derivación a Call Center. Servicio: UBICA. Timeout: 60s. Requiere intervención: Sí.

Estrategia de Trazabilidad

Principio fundamental: Las 3 tablas de auditoría (HistorialEstados, AuditoriaCambiosDatos, RegistroServiciosExternos) son de SOLO INSERCIÓN. No se permite UPDATE ni DELETE en estas tablas bajo ninguna circunstancia.

Capa 1: Historial de Estados

Cada transición de estado genera un registro inmutable que permite reconstruir la línea de tiempo completa del estudio. 

-- Ejemplo de registro generado al cambiar de BORRADOR a EN_PROGRESO:
INSERT INTO HistorialEstados (IdEstudio, IdEstadoAnterior, IdEstadoNuevo, 
    IdPasoRelacionado, TipoUsuario, MotivoTransicion)
VALUES (12345, 1, 2, 2, 'SISTEMA', 'Iniciar procesamiento del estudio');

Capa 2: Auditoría de Cambios

Cuando un dato del cliente cambia durante un estudio activo, se registra el valor anterior y el nuevo. 

-- Ejemplo: Cliente cambia su correo durante el estudio
INSERT INTO AuditoriaCambiosDatos (IdEstudio, NitTercero, NombreTabla, 
    NombreCampo, ValorAnterior, ValorNuevo, TipoUsuario)
VALUES (12345, '1098765432', 'terceros', 'mail', 
    'viejo@email.com', 'nuevo@email.com', 'ASESOR');

Capa 3: Logging de Servicios Externos

Cada invocación a un servicio externo se registra con el payload completo de request y response. 

-- Ejemplo: Invocación a Preselecta
INSERT INTO RegistroServiciosExternos (IdEstudio, IdPaso, NombreServicio, 
    URLEndpoint, PayloadRequest, PayloadResponse, CodigoHTTPRespuesta,
    ResultadoInterpretado, DuracionMs)
VALUES (12345, 9, 'PRESELECTA', 'https://api.preselecta.co/consultar',
    '{"documento":"1098765432","primerApellido":"Garcia"}',
    '{"status":1,"score":650,"viable":true}', 200, 'EXITOSO', 1523);

Flujo de Detección de Fraude y Escalamiento Nuevo v2.2

Este módulo describe cómo las 6 nuevas tablas de v2.2 se articulan para detectar, registrar y escalar comportamientos sospechosos durante el flujo de otorgamiento. El diseño sigue el principio de inmutabilidad total: cada evento de seguridad genera un registro que nunca puede ser modificado ni eliminado.

Principio rector: El sistema detecta fraude correlacionando eventos en el tiempo — no evalúa cada acción de forma aislada. La combinación "OTP fallido → cambio de email → nuevo OTP" es el patrón crítico que este módulo está diseñado para capturar.

6.1 Caso de Uso Completo: Cambio de Email Post-OTP Fallido

6.4 Vista del Asesor de Fábrica

El diseño permite que un asesor reconstruya el caso completo con una sola consulta SQL. No necesita navegar múltiples pantallas ni cruzar tablas manualmente. 

-- Consulta completa del caso para el asesor:
SELECT
    e.IdEscalamiento,
    cm.Nombre                     AS MotivoEscalamiento,
    cm.Origen                     AS TipoOrigen,
    ec.IdCorrelacion              AS RefEstudio,
    e.DescripcionContexto,
    e.PasoEnQueEscalo,
    e.SnapshotDatosCliente,
    e.EscaladoPorSistema,
    e.EstadoEscalamiento,
    e.FechaCreacion               AS FechaEscalamiento,

    -- Alerta de fraude que lo originó
    af.IdAlerta,
    rf.Nombre                     AS ReglaFraude,
    rf.NivelRiesgo,
    af.CampoAfectado,
    af.ValorAnterior,
    af.ValorNuevo,
    af.ContextoJSON,

    -- Log de intentos OTP relacionados
    (SELECT COUNT(*) FROM LogValidacionesOTP lv
     WHERE lv.IdEstudio = e.IdEstudio
       AND lv.ResultadoIntento IN ('FALLIDO_HASH','EXPIRADO')
       AND lv.FechaIntento >= DATEADD(HOUR, -1, e.FechaCreacion)
    )                             AS FallosOTPUltimaHora,

    -- Cambios de datos sensibles relacionados
    (SELECT COUNT(*) FROM HistorialDatosSensibles hds
     WHERE hds.IdEstudio = e.IdEstudio
       AND hds.EsPostFalloOTP = 1
       AND hds.FechaCambio >= DATEADD(HOUR, -1, e.FechaCreacion)
    )                             AS CambiosDatosSensiblesPostOTP

FROM EscalamientosFabrica e
JOIN CatalogoMotivosEscalamiento cm ON e.IdMotivoEscalamiento = cm.IdMotivo
JOIN EstudiosCredito ec ON e.IdEstudio = ec.IdEstudio
LEFT JOIN AlertasFraude af ON e.IdAlertaOrigen = af.IdAlerta
LEFT JOIN CatalogoReglasFraude rf ON af.IdReglaFraude = rf.IdReglaFraude
WHERE e.IdEscalamiento = @IdEscalamiento;

Para el asesor: Los campos SnapshotDatosCliente y ContextoJSON contienen el estado completo del cliente en el momento exacto del evento — no el estado actual. Esto es crítico para el análisis forense: los datos actuales pueden haber cambiado.

7.8 Consulta Completa del Asesor de Fotografías (v2.6)

En el diseño unificado, la información de revisión está inline en FotografiasEstudio. La consulta del asesor solo necesita un LEFT JOIN a RevisionesFotografia para el historial de auditoría detallado y a SolicitudesRecarga para la solicitud activa (si existe). 

-- Consulta completa de fotografías para el asesor (v2.6 — diseño unificado):
SELECT
    fe.TipoFotografia,                            -- SELFIE, DOCUMENTO_FRONTAL, DOCUMENTO_TRASERO
    fe.EstadoRevision,                            -- PENDIENTE, APROBADA_AUTO, APROBADA_ASESOR, RECHAZADA, REEMPLAZADA
    fe.EsVigente,                                 -- 1 = foto activa para este tipo
    fe.UrlArchivo,
    fe.FechaCaptura,
    fe.MetodoRevision,                            -- AUTOMATICO, MANUAL_ASESOR (NULL si PENDIENTE)
    fe.MotivoRechazo,                             -- inline — motivo de rechazo si aplica
    fe.PorcentajeCoincidencia,                    -- % match facial (solo SELFIE)
    fe.PruebaVidaExitosa,                         -- resultado prueba de vida (solo SELFIE)
    fe.FechaRevision,

    -- Solicitud de recarga activa (si existe)
    sr.EstadoSolicitud                            AS EstadoRecarga,
    sr.FechaExpiracion                            AS ExpiraRecarga

FROM FotografiasEstudio fe
LEFT JOIN SolicitudesRecarga sr
       ON sr.IdFotografiaAnterior = fe.IdFotografia
      AND sr.EstadoSolicitud IN ('GENERADO', 'ENVIADO')

WHERE fe.IdEstudio = @IdEstudio
ORDER BY fe.TipoFotografia, fe.FechaCaptura DESC;

-- Para historial de auditoría de decisiones humanas:
SELECT rv.*
FROM RevisionesFotografia rv
WHERE rv.IdEstudio = @IdEstudio
ORDER BY rv.FechaRevision DESC;

División de Responsabilidades: Backend vs Frontend Nuevo v2.5

Una confusión frecuente en el diseño del LOS es mezclar las responsabilidades del Backend con las del Frontend (enrutador/app). Esta sección establece el límite exacto: qué le pertenece a cada capa.

Principio rector: El Backend solo contiene lógica de negocio pura — reglas que vienen del dominio del crédito. El Frontend solo contiene lógica de presentación y navegación. Ninguno invade el territorio del otro.

🏛️ Backend — Lógica de Negocio Pura

Reglas que provienen del dominio crediticio. Inmutables desde el Frontend.

🖥️ Frontend / Enrutador — Presentación y Navegación

Duración de URLs, estado de pantallas, redirecciones por resultado.

¿Qué maneja el Backend?

ResponsabilidadEjemplo ConcretoJustificación
Reglas de expiración de OTP "El OTP expira en 5 minutos" Es una regla de negocio definida por el área de riesgo — no puede cambiarse sin aprobación del negocio
Límite de intentos "Máximo 3 intentos de OTP antes de bloqueo" Regla antifraude. Si el Frontend lo controlara, podría ser eludida manipulando la app
Vigencia del token de acceso "JWT válido por 30 minutos" Seguridad corporativa — determina cuánto tiempo es válida una sesión autenticada
Elegibilidad crediticia "El cliente tiene cartera morosa activa" Dato que viene del ERP QUAC — el Frontend no tiene acceso ni debería tenerlo
Transiciones de estado válidas "Solo se puede pasar de EN_PROGRESO a REVISION_FABRICA si biometría fue exitosa" Definido en TransicionesEstado — la máquina de estados es del Backend
Periodos de enfriamiento "60 días de cooling-off tras rechazo por Preselecta" Parámetro en ConfiguracionReglasNegocio. El Frontend solo muestra la fecha

Token de Acceso: Un Solo Origen de Verdad

Regla de diseño: Solo existe un tipo de token de acceso: el JWT (Bearer Token). No hay tokens propietarios, cookies de sesión, ni tokens de múltiples tipos. La diferencia está en quién lo emite y qué claims contiene.

Resumen del principio: El Backend valida el JWT en cada request, extrae los claims y aplica las reglas de negocio. El Frontend solo almacena el token (en memoria o sessionStorage), lo adjunta como Authorization: Bearer <token> y nunca interpreta su contenido.

Autenticación y Validación de Asesores Nuevo v2.5

En el flujo de bodega, el PC es compartido entre múltiples asesores durante el día. No existe una sesión individual por computador — cada asesor debe autenticarse antes de atender un cliente. La autenticación se realiza mediante Prueba de Vida facial con un microservicio externo.

Punto crítico de diseño: El asesor NO se auto-asigna. No es suficiente que ingrese su código — debe validarse biométricamente. Esto previene la suplantación de asesores y crea una cadena de custodia auditada para cada estudio de crédito.

Flujo Real de Autenticación del Asesor

1

Ingreso del Código de Asesor

El asesor ingresa su código (ej: ASE-00157) en la pantalla de inicio del PC de bodega. Este código es el identificador único en fab.OperadoresFabrica (GAP-19: reemplaza BERP_FABRICASOperadores).

2

Captura Biométrica

El sistema solicita al asesor que mire a la cámara del PC de bodega. Se captura una foto de prueba de vida (faceliveness) en tiempo real.

3

Llamada al Microservicio de Biometría

La API LOS llama al microservicio externo de Prueba de Vida: POST /ext/biometria/prueba-vida. El microservicio compara la foto capturada contra la plantilla biométrica registrada del asesor.

4

Registro y Resultado

El resultado se registra en ValidacionesAsesor (éxito o falla). Si exitoso, se emite un JWT con rol ASESOR_FABRICAS. Si falla, el intento queda auditado y se bloquea el acceso.

Concurrencia Optimista e Idempotencia — Guía Práctica Nuevo v2.5

Dos mecanismos de protección son indispensables para un sistema financiero multicanal. Esta sección los explica con ejemplos reales del día a día en la bodega y en la web.

🔑 Idempotencia

Garantiza que ejecutar la misma operación múltiples veces produce el mismo resultado que ejecutarla una sola vez.

🔒 Concurrencia Optimista

Permite que múltiples usuarios trabajen sobre el mismo registro sin bloquearlo, detectando y rechazando modificaciones conflictivas.

Ejemplo 1 — Doble clic del asesor (Idempotencia)

Escenario real: La asesora María en la bodega de Medellín hace doble clic en el botón "Aprobar Estudio" porque la respuesta tardó 2 segundos. Su conexión es lenta.

Sin protección ❌Con ClaveIdempotencia ✅
Se crean 2 aprobaciones en la base de datos El segundo request llega con el mismo UUID → el UNIQUE INDEX sobre ClaveIdempotencia lo rechaza instantáneamente
El cupo se desembolsa dos veces La API retorna HTTP 409 Conflict con next_action: ERROR_IDEMPOTENCY
Requiere proceso de reversión manual por el área de cartera El Frontend muestra la respuesta original del primer request al asesor

Flujo técnico — Cómo funciona el UNIQUE INDEX

── Request 1 (clic 1) ─────────────────────────────────────────────────────────
POST /tienda/solicitud/EST-2026-00123/activar-cupo
Headers: X-Idempotency-Key: "idem-abc-789-xyz"
Body:    { "idValidacionAsesor": 4521, "tipoCierre": "EXPRESS" }

Backend:
  1. Verifica UNIQUE INDEX en EstudiosCredito.ClaveIdempotencia = "idem-abc-789-xyz"
  2. No existe → ejecuta la activación
  3. UPDATE EstudiosCredito SET IdEstadoActual = CUPO_ACTIVO, ClaveIdempotencia = "idem-abc-789-xyz"
  4. Retorna HTTP 200 { "next_action": "FINAL_SUCCESS", ... }

── Request 2 (clic 2, 800ms después) ─────────────────────────────────────────
POST /tienda/solicitud/EST-2026-00123/activar-cupo
Headers: X-Idempotency-Key: "idem-abc-789-xyz"   ← mismo UUID

Backend:
  1. Verifica UNIQUE INDEX en EstudiosCredito.ClaveIdempotencia = "idem-abc-789-xyz"
  2. YA EXISTE → no ejecuta nada, retorna la respuesta cacheada del request 1
  3. Retorna HTTP 409 { "next_action": "ERROR_IDEMPOTENCY", "original_response": {...} }

Frontend:
  Recibe HTTP 409 → muestra la pantalla de "Cupo activado exitosamente" (respuesta original)

Ejemplo 2 — Cliente y asesor abren el estudio al mismo tiempo (Concurrencia Optimista)

Escenario real: El cliente Juan abre su estudio en su celular (flujo web) para actualizar su dirección. Al mismo tiempo, el asesor Pedro lo tiene abierto en el PC de la bodega para agregar una nota sobre la visita.

T+0:00  Juan (celular)  abre el estudio → Backend retorna { VersionFila: "0x00000000000007D1" }
T+0:00  Pedro (PC)      abre el estudio → Backend retorna { VersionFila: "0x00000000000007D1" }
         (ambos tienen la misma versión de la fila — el estudio no ha sido modificado)

T+0:15  Juan actualiza su dirección:
          PUT /web/solicitud/EST-2026-00123/datos-direccion
          Body: { "ciudad": "Manizales", "VersionFila": "0x00000000000007D1" }

Backend:
  UPDATE EstudiosCredito
  SET CiudadCapturada = 'Manizales', VersionFila = NEXT_ROW_VERSION()
  WHERE IdEstudio = 123
    AND VersionFila = 0x00000000000007D1  ← condición de concurrencia

  → Afecta 1 fila ✓  → Nueva VersionFila: "0x00000000000007D2"
  → HTTP 200 { "next_action": "ADVANCE_STEP" }

T+0:18  Pedro agrega nota (tiene aún VersionFila vieja = 0x7D1):
          POST /tienda/solicitud/EST-2026-00123/agregar-nota
          Body: { "nota": "Cliente vive cerca del parque", "VersionFila": "0x00000000000007D1" }

Backend:
  UPDATE EstudiosCredito
  SET NotaAsesor = 'Cliente vive cerca del parque', VersionFila = NEXT_ROW_VERSION()
  WHERE IdEstudio = 123
    AND VersionFila = 0x00000000000007D1  ← ya no coincide (está en 0x7D2)

  → Afecta 0 filas ✗
  → HTTP 409 { "next_action": "ERROR_CONCURRENCY",
               "mensaje": "Este estudio fue modificado por otro usuario. Recarga para ver los cambios." }

Pedro recibe la alerta → recarga → ve la dirección actualizada por Juan → puede agregar su nota con la nueva versión.

¿Por qué concurrencia optimista es mejor que bloqueo pesimista?

AspectoConcurrencia Optimista ✅Bloqueo Pesimista (SELECT FOR UPDATE)
Congela la fila No — múltiples usuarios pueden leer libremente Sí — bloquea la fila para todos los demás desde que se abre el registro
Escalabilidad Alta — no hay recursos retenidos en el servidor de BD Baja — si el asesor abre un estudio y va a almorzar, la fila queda bloqueada por horas
Riesgo de deadlock Ninguno — los conflictos se detectan al momento de escritura Alto — dos procesos esperando locks del otro generan deadlocks
Implementación en SQL Server VersionFila ROWVERSION — columna automática, cero código adicional WITH (UPDLOCK, HOLDLOCK) — gestión manual de transactions
Frecuencia de conflictos real Muy baja — los conflictos simultáneos genuinos son raros en el flujo normal Irrelevante — bloquea siempre, aunque no haya conflicto

Decisión de diseño: El campo VersionFila ROWVERSION ya está en EstudiosCredito. SQL Server lo actualiza automáticamente en cada UPDATE. El LOS solo necesita incluirlo en el WHERE de cada actualización y retornarlo en cada respuesta dentro del campo meta.row_version.

Reglas de implementación de Idempotencia en el LOS

ReglaDetalle
Header obligatorio en mutaciones Todo POST/PUT/PATCH debe incluir X-Idempotency-Key: {uuid}. El servidor retorna HTTP 400 si falta en operaciones que lo requieren.
TTL del registro Las claves de idempotencia se mantienen por 24 horas. Después de ese periodo, el mismo UUID puede reutilizarse (muy improbable en la práctica).
GET/HEAD son idempotentes por definición Las consultas no necesitan X-Idempotency-Key — releer siempre retorna el estado actual sin efectos secundarios.
Respuesta en 409 El HTTP 409 por idempotencia incluye la respuesta original en original_response. El Frontend puede usarla directamente.
Generación del UUID El UUID debe generarse en el cliente (Frontend/App) antes de enviar el request, no en el Backend. Esto garantiza que el mismo intento tenga siempre el mismo UUID aunque haya retries.
