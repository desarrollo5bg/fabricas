Arquitectura de Datos v2.3 — Fábricas de Crédito QUAC

Motor: SQL Server 2019+ Versión: 2.3 Fecha: 13 de abril de 2026 Tablas Nuevas: 27 Tablas Modificadas: 7

Este documento describe el modelo de datos empresarial versión 2.3 para el Sistema de Otorgamiento de Crédito (Loan Origination System - LOS) de QUAC. Esta versión implementa la "Fusión Inteligente": reutiliza las tablas existentes en producción del ERP QUAC y les añade capacidades de trazabilidad, auditoría y automatización sin romper la operación actual. La versión 2.2 añadió el sistema de detección de fraude y escalamiento con 6 nuevas tablas especializadas. La versión 2.3 añade el módulo de gestión de fotografías con 5 nuevas tablas para el ciclo de vida completo de fotos obligatorias, revisión humana y re-subida via link.

Innovación clave: A diferencia de un diseño desde cero, esta versión respeta el trabajo existente integrando las tablas QUAC.dbo.bodegas, QUAC.dbo.KCRM_CadenaCreditos y operadores, mientras añade la capa de configuración (máquina de estados), transaccional y auditoría que faltaba. Para QUAC.dbo.terceros se creó una tabla propia (TercerosFabricas) que lee de ella mediante FK por NIT, sin alterar la tabla de producción.

Resumen Ejecutivo

5 Tablas de Configuración

Fases, Pasos, Estados, Transiciones y Reglas parametrizables sin código.

6 Tablas Transaccionales

Estudios, OTP, Riesgo, Biometría, Contactabilidad y Consentimientos.

3 Tablas de Auditoría

Historial de estados, cambios de datos y logging de servicios externos.

2 Tablas Extendidas

KCRM_CadenaCreditos y BERP_FABRICASOperadores con columnas de fábricas.

1 Tabla Propia (terceros)

TercerosFabricas como fuente de verdad. Lee de terceros sin modificarlo.

6 Tablas Antifraude Nuevo v2.2

Detección de fraude, escalamiento a fábrica, log OTP granular e historial de datos sensibles.

5 Tablas Fotografías Nuevo v2.3

Ciclo de vida de fotos obligatorias, revisión por asesor, re-subida via link y auditoría inmutable.

Principales mejoras sobre el diseño anterior

  • Máquina de estados inmutable — Cada cambio de estado genera un registro en HistorialEstados que permite reconstruir la línea de tiempo completa.
  • Auditoría de datos mutables — Cualquier cambio en datos del cliente durante un estudio se registra en AuditoriaCambiosDatos.
  • Logging completo de servicios — Cada invocación a buró, biometría, FOSYGA, UBICA, OTP queda registrada con el payload completo en RegistroServiciosExternos.
  • Cursor de pausa/reanudación — El campo IdPasoActual en EstudiosCredito permite que el cliente abandone y retome el proceso.
  • Parameterización total — Las reglas de negocio (días de enfriamiento, intentos OTP, timeouts) están en ConfiguracionReglasNegocio y pueden cambiarse sin deploy.

Arquitectura del Modelo de Datos

El modelo se organiza en 4 grupos lógicos que respetan el orden de dependencia (maestras → configuración → transaccionales → auditoría):

1

Tablas Existentes del ERP (Extendidas + Tabla Propia)

QUAC.dbo.bodegas, QUAC.dbo.KCRM_CadenaCreditos, BERP_FABRICASOperadores (extendidas). TercerosFabricas es tabla propia que lee de terceros mediante FK por NIT sin modificar la tabla de producción.

2

Tablas de Configuración (Nuevas)

Definen el flujo, estados y reglas de negocio. FasesEstudio, PasosEstudio, CatalogoEstados, TransicionesEstado, ConfiguracionReglasNegocio. Permiten modificar el comportamiento sin tocar código.

3

Tablas Transaccionales (Nuevas)

Registran las operaciones del proceso. EstudiosCredito (orquestador central), RetosSeguridad, EvaluacionesRiesgo, RegistrosBiometria, ValidacionesContactabilidad, ConsentimientosLegales.

4

Tablas de Auditoría (Nuevas)

Trazabilidad inmutable. HistorialEstados, AuditoriaCambiosDatos, RegistroServiciosExternos. REGLA: Solo INSERT, nunca UPDATE ni DELETE.

Estrategia de Integración

Principio rector: Las tablas existentes NUNCA se eliminan ni se altera su estructura original. Solo se les añaden columnas al final mediante ALTER TABLE ADD. Esto garantiza backwards compatibility con el ERP QUAC existente. Excepción: QUAC.dbo.terceros es demasiado grande para modificar, por lo que se crea una tabla propia que lee de ella mediante FK por NIT.

Estrategia para QUAC.dbo.terceros

-- Tabla PROPIA que referencia a terceros sin modificarlo:
CREATE TABLE dbo.TercerosFabricas (
    IdTerceroFabricas       INT IDENTITY(1,1) NOT NULL,
    NitTercero              VARCHAR(20) NOT NULL,  -- FK a terceros.nit
    NombreTercero           VARCHAR(200) NULL,
    EstadoTercero           VARCHAR(20) NOT NULL DEFAULT 'ACTIVO',
    TieneCupoActivo        BIT NOT NULL DEFAULT 0,
    EstaBloqueadoFabricas  BIT NOT NULL DEFAULT 0,
    MotivoBloqueo          VARCHAR(100) NULL,
    FechaBloqueo           DATETIME2 NULL,
    FechaDesbloqueo        DATETIME2 NULL,  -- Cooling-off
    TieneRegistroBiometrico BIT NOT NULL DEFAULT 0,
    PuntajeCredito         DECIMAL(5,2) NULL,
    FechaCreacion          DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    FechaModificacion      DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    ...
    CONSTRAINT FK_TercerosFabricas_Terceros FOREIGN KEY (NitTercero)
        REFERENCES QUAC.dbo.terceros(nit)
);

Flujo de datos: Leer de terceros para validar existencia → Escribir en TercerosFabricas como fuente de verdad → Sincronizar actualizaciones de vuelta a terceros según reglas de negocio.

Columnas añadidas a QUAC.dbo.KCRM_CadenaCreditos

ALTER TABLE QUAC.dbo.KCRM_CadenaCreditos ADD
    EstadoActualFabricas     VARCHAR(20) NULL, -- ACTIVO, BLOQUEADO, CANCELADO
    MotivoBloqueoFabricas    VARCHAR(50) NULL, -- MORA, FRAUDE, SOLICITUD_CLIENTE
    FechaCancelacionFabricas DATETIME2 NULL,  -- Para regla "renunció en XXX días"
    ElegibleReactivacion     BIT DEFAULT 0;   -- Reactivación exprés

Orden de ejecución del script

  1. Crear tablas de configuración — Sin dependencias externas

  4. Crear tablas transaccionales — Dependen de configuración
  5. Crear tablas de auditoría — Dependen de transaccionales

4

FASE 4: Validaciones de Riesgo (4 pasos)

VALIDAR_LISTAS — Consulta listas restrictivas. Servicio: LISTAS_RESTRICTIVAS. Timeout: 30s.

CONSULTAR_BURO — Consulta historial crediticio. Servicio: BURO_CREDITO. Timeout: 60s.

EVALUAR_PRESELECTA — Motor de decisión. Servicio: PRESELECTA. Timeout: 60s.

VALIDAR_FOSYGA — Verificación seguridad social. Servicio: FOSYGA. Timeout: 30s.

FASE 5: Límite de Crédito (1 paso)

7

FASE 7: Activación (1 paso)

ACTIVACION_CUPO — Validación UBICA y activación automática o derivación a Call Center. Servicio: UBICA. Timeout: 60s. Requiere intervención: Sí.

Estrategia de Trazabilidad

Principio fundamental: Las 3 tablas de auditoría (HistorialEstados, AuditoriaCambiosDatos, RegistroServiciosExternos) son de SOLO INSERCIÓN. No se permite UPDATE ni DELETE en estas tablas bajo ninguna circunstancia.

Capa 1: Historial de Estados

Cada transición de estado genera un registro inmutable que permite reconstruir la línea de tiempo completa del estudio. 

-- Ejemplo de registro generado al cambiar de BORRADOR a EN_PROGRESO:
INSERT INTO HistorialEstados (IdEstudio, IdEstadoAnterior, IdEstadoNuevo, 
    IdPasoRelacionado, TipoUsuario, MotivoTransicion)
VALUES (12345, 1, 2, 2, 'SISTEMA', 'Iniciar procesamiento del estudio');

Capa 2: Auditoría de Cambios

Cuando un dato del cliente cambia durante un estudio activo, se registra el valor anterior y el nuevo. 

-- Ejemplo: Cliente cambia su correo durante el estudio
INSERT INTO AuditoriaCambiosDatos (IdEstudio, NitTercero, NombreTabla, 
    NombreCampo, ValorAnterior, ValorNuevo, TipoUsuario)
VALUES (12345, '1098765432', 'terceros', 'mail', 
    'viejo@email.com', 'nuevo@email.com', 'ASESOR');

Capa 3: Logging de Servicios Externos

Cada invocación a un servicio externo se registra con el payload completo de request y response. 

-- Ejemplo: Invocación a Preselecta
INSERT INTO RegistroServiciosExternos (IdEstudio, IdPaso, NombreServicio, 
    URLEndpoint, PayloadRequest, PayloadResponse, CodigoHTTPRespuesta,
    ResultadoInterpretado, DuracionMs)
VALUES (12345, 9, 'PRESELECTA', 'https://api.preselecta.co/consultar',
    '{"documento":"1098765432","primerApellido":"Garcia"}',
    '{"status":1,"score":650,"viable":true}', 200, 'EXITOSO', 1523);

Flujo de Detección de Fraude y Escalamiento Nuevo v2.2

Este módulo describe cómo las 6 nuevas tablas de v2.2 se articulan para detectar, registrar y escalar comportamientos sospechosos durante el flujo de otorgamiento. El diseño sigue el principio de inmutabilidad total: cada evento de seguridad genera un registro que nunca puede ser modificado ni eliminado.

Principio rector: El sistema detecta fraude correlacionando eventos en el tiempo — no evalúa cada acción de forma aislada. La combinación "OTP fallido → cambio de email → nuevo OTP" es el patrón crítico que este módulo está diseñado para capturar.

6.1 Caso de Uso Completo: Cambio de Email Post-OTP Fallido

Este es el escenario de mayor riesgo: un actor malicioso que tiene acceso al email original del cliente falla el OTP, luego modifica el email a uno bajo su control, y solicita un nuevo OTP al email que controla.

Timeline del Evento

T+00:00  Cliente inicia estudio (EstudiosCredito creado, estado = EN_PROGRESO)
         └─► INSERT RetosSeguridad: Reto OTP enviado a email@cliente.com

T+00:30  Cliente ingresa código incorrecto

T+01:00  Cliente vuelve a fallar el código

               DireccionEnvio: 'email@cliente.com', IP: '190.x.x.x' }

T+01:15  ⚠ EVENTO SOSPECHOSO: Cliente cambia email durante reto OTP activo

               CampoCambiado: 'EmailCliente',
               ValorOriginal: 'email@cliente.com',

               IdEstudio: [...], IdReglaFraude: 1,

               ValorAnterior: 'email@cliente.com',
               ValorNuevo: 'atacante@otro.com',
               AccionTomada: 'PENDIENTE'
             }

T+01:17  Sistema ejecuta AccionAutomatica = ESCALAR
         ├─► UPDATE EstudiosCredito: IdEstadoActual = REVISION_FABRICA
         ├─► UPDATE EstudiosCredito: IdEscalamientoActivo = [nuevo IdEscalamiento]

               IdEstadoAnterior: EN_PROGRESO, IdEstadoNuevo: REVISION_FABRICA,
               MotivoTransicion: 'EMAIL_CHANGE_POST_OTP_FAIL — escalamiento automático'

Resolución por el Asesor de Fábrica

Asesor abre EscalamientosFabrica y ve:
  - Motivo: "OTP fallido + cambio de email"
  - Email original: email@cliente.com
  - Email nuevo: atacante@otro.com

  - IP: 190.x.x.x (misma en todos los eventos)

  └─► UPDATE AlertasFraude: { AccionTomada: 'DESCARTADO' }

6.4 Vista del Asesor de Fábrica

El diseño permite que un asesor reconstruya el caso completo con una sola consulta SQL. No necesita navegar múltiples pantallas ni cruzar tablas manualmente. 

-- Consulta completa del caso para el asesor:
SELECT
    e.IdEscalamiento,
    cm.Nombre                     AS MotivoEscalamiento,
    cm.Origen                     AS TipoOrigen,
    ec.ClaveIdempotencia          AS RefEstudio,
    e.DescripcionContexto,
    e.PasoEnQueEscalo,
    e.SnapshotDatosCliente,
    e.EscaladoPorSistema,
    e.EstadoEscalamiento,
    e.FechaCreacion               AS FechaEscalamiento,

    -- Alerta de fraude que lo originó
    af.IdAlerta,
    rf.Nombre                     AS ReglaFraude,
    rf.NivelRiesgo,
    af.CampoAfectado,
    af.ValorAnterior,
    af.ValorNuevo,
    af.ContextoJSON,

    -- Log de intentos OTP relacionados
    (SELECT COUNT(*) FROM LogValidacionesOTP lv
     WHERE lv.IdEstudio = e.IdEstudio
       AND lv.ResultadoIntento IN ('FALLIDO_HASH','EXPIRADO')
       AND lv.FechaIntento >= DATEADD(HOUR, -1, e.FechaCreacion)
    )                             AS FallosOTPUltimaHora,

    -- Cambios de datos sensibles relacionados
    (SELECT COUNT(*) FROM HistorialDatosSensibles hds
     WHERE hds.IdEstudio = e.IdEstudio
       AND hds.EsPostFalloOTP = 1
       AND hds.FechaCambio >= DATEADD(HOUR, -1, e.FechaCreacion)
    )                             AS CambiosDatosSensiblesPostOTP

FROM EscalamientosFabrica e
JOIN CatalogoMotivosEscalamiento cm ON e.IdMotivoEscalamiento = cm.IdMotivo
JOIN EstudiosCredito ec ON e.IdEstudio = ec.IdEstudio
LEFT JOIN AlertasFraude af ON e.IdAlertaOrigen = af.IdAlerta
LEFT JOIN CatalogoReglasFraude rf ON af.IdReglaFraude = rf.IdReglaFraude
WHERE e.IdEscalamiento = @IdEscalamiento;

Para el asesor: Los campos SnapshotDatosCliente y ContextoJSON contienen el estado completo del cliente en el momento exacto del evento — no el estado actual. Esto es crítico para el análisis forense: los datos actuales pueden haber cambiado.

7.3 Proceso de Revisión por el Asesor

Cuando el estudio llega al estado FOTOS_EN_REVISION, el asesor de fábrica revisa las 3 fotografías y registra su decisión en RevisionesFotografia. 

T+00:00  Cliente completa carga de las 3 fotos
         └─► UPDATE EstudiosCredito: IdEstadoActual = FOTOS_EN_REVISION
         └─► FotografiasEstudio (x3): EstadoFoto = EN_REVISION

T+00:05  Asesor abre el panel de fotografías del estudio
         ├─► Visualiza FOTO_FRONTAL_DOC → calidad OK
         │   └─► INSERT RevisionesFotografia: { ResultadoRevision: 'APROBADA', IdAsesor: [...] }
         │   └─► UPDATE FotografiasEstudio: EstadoFoto = 'APROBADA'
         │   └─► UPDATE EstudiosCredito: FotografiasAprobadas = 1
         │
         ├─► Visualiza FOTO_TRASERA_DOC → calidad OK
         │   └─► INSERT RevisionesFotografia: { ResultadoRevision: 'APROBADA' }
         │   └─► UPDATE FotografiasEstudio: EstadoFoto = 'APROBADA'
         │   └─► UPDATE EstudiosCredito: FotografiasAprobadas = 2
         │
         └─► Visualiza SELFIE → rostro no visible claramente
             └─► INSERT RevisionesFotografia: {
                   ResultadoRevision: 'RECHAZADA',
                   MotivoRechazo: 'Imagen borrosa — rostro no distinguible',
                   IdAsesor: [...]
                 }
             └─► UPDATE FotografiasEstudio: EstadoFoto = 'RECHAZADA'
             └─► INSERT SolicitudesRecarga: {
                   IdFotografia: [...], UrlCargaFirmada: 'https://storage/...',
                   FechaExpiracion: NOW() + 48h, EstadoSolicitud: 'GENERADO'
                 }
             └─► UPDATE EstudiosCredito: EstadoRevisionFotos = 'CON_RECHAZOS'

7.4 Sistema de Re-carga de Fotografías

Cuando una foto es rechazada, SolicitudesRecarga gestiona el enlace de carga seguro que se envía al cliente. El enlace expira y tiene estado propio.

Estado Solicitud Significado Transición Siguiente
GENERADO Enlace creado, aún no enviado o no usado ENVIADO → USADO / EXPIRADO / CANCELADO
ENVIADO Enlace notificado al cliente (email/SMS) USADO / EXPIRADO / CANCELADO
USADO Cliente subió nueva foto usando el enlace Estado terminal
EXPIRADO Enlace vencido sin ser usado (FechaExpiracion < NOW()) Estado terminal — se puede generar uno nuevo
CANCELADO Enlace invalidado manualmente por el asesor Estado terminal

7.5 Escenarios de Ejemplo

Escenario A — Flujo Feliz (las 3 fotos aprobadas en primera revisión)

Cliente sube 3 fotos → EstadosCredito pasa a FOTOS_EN_REVISION
Asesor aprueba las 3 → FotografiasAprobadas = 3
                     → EstadoRevisionFotos = 'APROBADO'
                     → EstudiosCredito pasa a estado biometría
                     → RegistrosBiometria se crea con FK a las 3 fotos aprobadas

Escenario B — Selfie Rechazada y Recargada

Asesor rechaza SELFIE (borrosa) → SolicitudesRecarga generada
                                 → EstadoRevisionFotos = 'CON_RECHAZOS'

Cliente recibe enlace → sube nueva selfie
                      → FotografiasEstudio (selfie v1) → REEMPLAZADA
                      → FotografiasEstudio (selfie v2) → CARGADA
                      → INSERT HistorialFotografias (preserva URL v1)
                      → SolicitudesRecarga → USADO

Asesor revisa selfie v2 → APROBADA
                        → FotografiasAprobadas = 3
                        → EstadoRevisionFotos = 'APROBADO'

Escenario C — Foto Faltante y Enlace Expirado

Asesor rechaza FOTO_FRONTAL_DOC → SolicitudesRecarga generada (expira en 48h)
                                 → Notificación enviada: EstadoSolicitud = ENVIADO

48 horas después → Cliente no subió la foto
                 → Job nocturno detecta FechaExpiracion < NOW()
                 → SolicitudesRecarga → EXPIRADO

Asesor genera nuevo enlace → Nueva SolicitudesRecarga (EstadoSolicitud: GENERADO)
                           → Enlace anterior queda EXPIRADO (trazabilidad)

7.6 Conexión con el Módulo Biométrico

Una vez que FotografiasAprobadas = 3, el paso biométrico puede iniciarse. RegistrosBiometria almacena FK directas a las fotos aprobadas que se usaron en la comparación, garantizando auditoría cruzada completa. 

EstudiosCredito
  │  FotografiasAprobadas = 3
  │  EstadoRevisionFotos = APROBADO
  │
  ▼ (desbloquea biometría)
RegistrosBiometria
  ├── IdFotografiaFrontal ──FK──► FotografiasEstudio (FOTO_FRONTAL_DOC, APROBADA)
  ├── IdFotografiaReverso ──FK──► FotografiasEstudio (FOTO_TRASERA_DOC, APROBADA)
  └── IdFotografiaSelfie  ──FK──► FotografiasEstudio (SELFIE, APROBADA)
          │
          │  Coincidencia facial (UmbralMatchFacial)
          ▼
      ResultadoBiometria = EXITOSO / FALLIDO / DERIVADO_FABRICA

Auditoría: Si la biometría es impugnada, RegistrosBiometria permite recuperar las URLs exactas de las imágenes que se usaron en la comparación — no las versiones actuales (que pueden haber sido reemplazadas), sino las versiones aprobadas en el momento del registro.

7.7 Reglas de Fraude Fotográfico

Las 4 reglas semilla fotográficas en CatalogoReglasFraude detectan los patrones de mayor riesgo:

Código de Regla Nivel Patrón Detectado Acción
FOTO_RECHAZADA_MULTIPLE_VECES MEDIO Misma foto rechazada más de N veces (posible intento de evadir validación) ESCALAR
MAX_VERSIONES_FOTO_SUPERADO ALTO NumeroVersion supera el límite configurado (abuso del sistema de recarga) ESCALAR
FOTO_DUPLICADA_OTRO_ESTUDIO CRITICO URL o hash de imagen coincide con una foto en otro estudio (fraude de identidad) BLOQUEAR
SELFIE_NO_COINCIDE_DOCUMENTO ALTO Algoritmo detecta que el rostro de la selfie no coincide con la foto del documento ESCALAR

7.8 Consulta Completa del Asesor de Fotografías

El asesor puede reconstruir el estado fotográfico completo de un estudio con una sola consulta SQL, incluyendo cada versión de cada foto y cada decisión de revisión tomada. 

-- Consulta completa de fotografías para el asesor:
SELECT
    ct.Nombre                     AS TipoFotografia,
    ct.EsObligatorio,
    fe.NumeroVersion,
    fe.EstadoFoto,
    fe.UrlAlmacenamiento,
    fe.FechaCreacion              AS FechaCarga,

    -- Última revisión del asesor sobre esta foto
    rv.ResultadoRevision,
    rv.MotivoRechazo,
    rv.NotasAsesor,
    rv.FechaRevision,

    -- Solicitud de recarga activa (si existe)
    sr.EstadoSolicitud            AS EstadoRecarga,
    sr.FechaExpiracion            AS ExpiraRecarga

FROM FotografiasEstudio fe
JOIN CatalogoTiposFotografia ct ON fe.IdTipoFotografia = ct.IdTipoFotografia
LEFT JOIN RevisionesFotografia rv ON rv.IdFotografia = fe.IdFotografia
    AND rv.IdRevision = (
        SELECT TOP 1 IdRevision
        FROM RevisionesFotografia
        WHERE IdFotografia = fe.IdFotografia
        ORDER BY FechaRevision DESC
    )
LEFT JOIN SolicitudesRecarga sr ON sr.IdFotografia = fe.IdFotografia
    AND sr.EstadoSolicitud IN ('GENERADO', 'ENVIADO')

WHERE fe.IdEstudio = @IdEstudio
ORDER BY ct.Nombre, fe.NumeroVersion DESC;

Consideraciones FinTech y Cumplimiento

Auditoría Regulatoria

Cada decisión de crédito es trazable desde la solicitud hasta el resultado, con timestamps exactos y responsables.

Aislamiento de Datos

Los consentimientos y cambios se registran inmutablemente, cumpliendo con normatividad de protección de datos.

Debugging Forense

Los payloads completos de servicios externos permiten reconstruir exactamente qué recibió y envió el sistema.

Escalabilidad

El diseño soporta 5,000-10,000 solicitudes/mes con índices optimizados para las consultas más frecuentes.

Seguridad de Datos

  • Tokens hash: Los OTP y tokens de seguridad se almacenan como hash, nunca en texto plano.
  • Direcciones IP: Se registra la IP del dispositivo en consentimientos para trazabilidad legal.
  • User Agent: Se captura el dispositivo/navegador para análisis de fraude.
  • Duraciones: El logging incluye tiempo de respuesta (ms) para detección de ataques de denegación de servicio.

Backwards Compatibility

  • Todas las tablas existentes mantienen su estructura original
  • Las nuevas columnas se añaden al final con valores por defecto seguros
  • Los procedures y vistas existentes siguen funcionando sin cambios
  • El nuevo código puede comenzar a usar las tablas de fábricas sin romper el código legacy
